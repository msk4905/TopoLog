# 일괄 실행 환경 복구 — v0.2.0-dev.6

GNS3와 연동 GNS3 VM을 준비한 뒤 TopoLog에서 수집합니다. 프로젝트와 노드는 미리 켜지 않습니다.

로컬 Dynamips·VPCS 실행 파일 설정이 누락되었으면 설치 경로를 찾아 자동 복구하며 원본 설정을 같은 비공개 폴더에 백업합니다. 유효한 사용자 지정 절대 경로와 원격 서버 설정은 유지합니다. 경로가 변경된 첫 실행에서는 수집을 시작하지 않고 서버 재시작을 안내합니다. 직접 경로를 편집할 필요는 없습니다.

Desktop 서버가 local=false이면 images 폴더 밖 IOS 이미지 경로가 거부될 수 있습니다. GNS3와 해당 Desktop 서버를 종료하고 GNS3가 새 서버를 시작하도록 안내합니다. TopoLog의 보조 서버 기동도 --local을 사용합니다. 다른 작업의 서버나 VM을 강제 종료하지 않습니다.

실행 중 **중지**를 누르면 터미널 설정과 TopoLog가 변경한 실행 상태의 복구를 시도하고 결과를 저장합니다. 취소된 노드와 미실행 노드를 구분합니다. 장비가 응답하지 않아 복원하지 못한 경우 복구 오류를 확인하세요. 프로세스를 강제 종료하면 이 절차를 끝내지 못할 수 있습니다.

ASA의 일반 EXEC(>)는 여전히 requires_privilege이며 enable 자동 처리는 없습니다. 기대값 편집과 기존 결과 재판정은 [사용 안내](CRITERIA_GUIDE.md)를 참고하세요.

# 일괄 실행 오류와 재실행

## Dynamips ID 충돌

`Dynamips identifier 1 is already used by another router`는 프로젝트 파일의 ID가 잘못되었다는 뜻으로 단정할 수 없습니다. GNS3 2.2.61의 별도 서버에서 다음 순서를 재현했습니다.

1. 서버에서 Dynamips를 찾지 못해 `Could not find Dynamips`로 라우터 생성이 실패합니다.
2. 실패한 생성 요청의 ID 예약이 서버 메모리에 남습니다.
3. 같은 요청을 다시 보내면 원래 오류 대신 ID 충돌이 반환됩니다.

TopoLog가 로컬 서버를 직접 시작할 때 설치 폴더의 Dynamips·uBridge·QEMU 실행 파일이 있는 경로를 자식 프로세스의 PATH에 전달하도록 수정했습니다. Windows 전체 PATH나 GNS3 설치 파일, 프로젝트의 라우터 ID를 변경하지 않습니다. 이미 실행 중인 서버에는 새 환경이 적용되지 않습니다.

### 현재 충돌 상태에서 다시 실행하기

1. 다른 GNS3 작업을 저장하고 진행 중인 TopoLog 수집을 마칩니다.
2. 문제가 발생한 GNS3 서버를 종료합니다. GNS3 창을 사용 중이었다면 종료하고, 작업 관리자에서 해당 `gns3server.exe`가 남아 있는지도 확인합니다. 다른 작업에서 사용하는 서버를 함께 종료하지 않습니다.
3. 수정된 `TopoLog-Batch.cmd`를 실행합니다. 로컬 서버를 새 환경으로 자동 기동한 뒤 프로젝트 폴더를 다시 처리합니다.

ID 충돌이 반복되면 GNS3 서버 로그의 **최초 라우터 생성 오류**를 확인합니다. Dynamips 경로 외에도 생성 실패 원인이 있을 수 있습니다. 사용자 지정 Dynamips 경로가 잘못되어 있다면 GNS3 설정에서 확인해야 합니다. TopoLog는 실행 중인 다른 서버를 강제 종료하거나 프로젝트 ID를 바꿔 우회하지 않습니다.

## ASA 수집 권한

`F2>`는 일반 EXEC 프롬프트입니다. 이번 실행에서 실패한 running-config·인터페이스·라우팅·ACL·NAT 수집에는 `F2#` 권한이 필요합니다. 현재 수집기는 OS를 식별한 뒤 `requires_privilege`로 기록하고 이유를 보고서에 표시합니다. enable이나 암호를 자동 입력하는 기능은 아직 없습니다.

## 판정과 실행 종료 코드

`inconclusive`와 종료 코드 2는 수집 실패 또는 검증 미완료를 의미합니다. 수집에 성공해도 검증 JSON의 기대값이 비어 있으면 정상 동작으로 판정하지 않습니다. 콘솔이 없는 기본 스위치는 API 구성은 보존하지만 콘솔 검증은 미지원입니다.

## 이번 수정의 검증 범위

- 합성 API·콘솔을 이용한 자동 검사 39개 통과.
- 별도 진단 서버에서 Dynamips 탐색 실패 후 ID 충돌로 이어지는 순서 재현.
- 수정된 경로에서 Dynamips 탐색 단계는 통과했으나, 작업 환경의 Windows DLL 실행 오류로 라우터 생성·부팅 완료는 검증하지 못함.
- 사용자 프로젝트 전체의 일괄 재실행과 동작 검증 완료 여부는 다음 실제 실행 결과로 확인해야 함.


## 실제 Desktop 서버 추가 진단 — 2026-11-04

10:14 결과에서 Desktop 전용 프로젝트 25개와 Desktop·VM 혼합 프로젝트 1개는 실패했고, VM 전용 프로젝트 1개에서는 IOS 라우터 4대 수집에 성공했습니다. ASA는 같은 VM에 있으며 권한 부족으로 미완료입니다. 별도의 빈 프로젝트 4개는 처리 완료 표시만으로 동작 검증 성공으로 볼 수 없습니다.

현재 Desktop 서버에 새 임시 프로젝트로 요청했을 때도 최초 오류는 `HTTP 409: Could not find Dynamips`였습니다. 진단 프로젝트는 삭제했고 장비를 부팅하지 않았습니다. 서버의 연결 표시가 녹색이어도 Dynamips 실행 파일을 찾지 못할 수 있습니다. 이번 실행은 기존 서버를 재사용했으므로, 먼저 해당 Desktop 서버를 완전히 종료한 뒤 수정된 TopoLog로 새로 시작해야 합니다.
